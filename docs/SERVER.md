# Сервер Jarvis («мозг» на ноутбуке)

Программа на Python, которая слушает плату по Wi-Fi (протокол: [PROTOCOL.md](PROTOCOL.md)), распознаёт речь,
спрашивает Gemini, озвучивает ответ клонированным голосом и отдаёт звук обратно на плату. Всё тяжёлое (распознавание
речи и голос) работает на видеокарте ноутбука, к Google ходит только текст. Версия сервера 0.4.0 (приходит на плату в
`welcome.server`, пишется первой строкой лога, `python -m jarvis_server --version`). Что нового в 0.4.0: управление ноутбуком голосом через Hyprland (программы, окна, громкость, музыка, сайты, блокировка, питание с подтверждением; раздел про управление ПК). Что нового в 0.3.2: в режиме `follow`
(продолжение без слова «Джарвис») ИИ сам решает, обращена ли фраза к Джарвису; если нет, плата получает только `state idle`,
ни текста, ни звука, и ход не запоминается (раздел «Режим follow: молчать, когда фраза не к Джарвису»); соединение с Google
держится 120 с вместо 5 и открывается заранее, как только человек начал говорить (раздел «Тёплое соединение с Google»); в
строке `TURN` новые ключи `llm_conn` и `why`. Что нового в 0.3.1: хедж-запросы к ИИ.
Если основная модель не дала первого слова за 2,5 с, тот же запрос параллельно уходит на запасную, и говорит та, что
ответила первой (раздел «Медленный ИИ: хедж-запросы»); в строке `TURN` новый ключ `llm_hedge`; необязательная заглушка
«Секунду, сэр.» (по умолчанию выключена). Что нового в 0.3.0 по сравнению с 0.2.0:
первое предложение длинного ответа озвучивается двумя кусками, чтобы Джарвис заговорил раньше (раздел «Быстрый первый
звук»); режим `follow`, продолжение разговора без слова «Джарвис» (раздел «Режимы разговора»); перебить Джарвиса
голосом: `abort` посреди ответа отменяет и сам синтез на видеокарте, а не только очередь (раздел «Как реализован
протокол»); Джарвис не произносит собственное имя; память разговора 20 обменов для игр.

```
плата --речь 16 кГц--> [Whisper large-v3-turbo] --текст--> [Gemini, потоком] --предложения--> [OmniVoice, клон голоса]
плата <--звук 24 кГц-- (подача по часам, не больше 1,5 с вперёд) <-------------------------------------+
```

## Установка (Давид)

Нужно: Arch Linux, видеокарта NVIDIA с драйвером, около 15 ГБ свободного места, включённый VPN (модели качаются с
huggingface.co, ИИ работает через Google), ключ Gemini и файл `jarvis_voice.zip` от Мирослава (образец голоса).

```
git clone https://github.com/telmiroslav/jarvis.git && cd jarvis && ./server/install.sh
```

(если репозиторий уже есть: `cd jarvis && git pull && ./server/install.sh`; повторный запуск безопасен и служит обновлением.)

Что делает установщик (по-русски объясняет каждый шаг, лог сохраняет в `~/jarvis-logs/server-install-*.log`):

1. Проверяет Arch, `nvidia-smi` (если драйвера нет, пишет, что поставить: `sudo pacman -S nvidia-open nvidia-utils`, и
   перезагрузку), версию драйвера (нужен 570+ для CUDA 12.8) и место на диске.
2. Спрашивает ключ Gemini (ввод скрытый; можно пропустить и позже выполнить `./server/set_key.sh`).
3. Спрашивает путь к `jarvis_voice.zip` (по умолчанию самый свежий `~/Downloads/jarvis_voice*.zip`), распаковывает
   в `~/.config/jarvis/voice/` (`ref.wav` или `ref.mp3` и `ref.txt`).
4. Один раз просит пароль sudo: `pacman -S --needed uv git` (если их нет) и правила UFW только для домашней сети
   `192.168.0.0/16`: UDP 47800 и TCP 47801 (если UFW включён; из интернета и из VPN порты остаются закрытыми).
5. Создаёт окружение `~/.local/share/jarvis/venv` (Python 3.12 от uv, PyTorch 2.8.0 для CUDA 12.8, остальное по
   `server/requirements.lock`, версии зафиксированы).
6. Заранее скачивает модели (распознавание около 1,6 ГБ, голос около 2,5 ГБ).
7. Ставит пользовательскую службу `jarvis-server.service` (`Restart=on-failure`).
8. Самопроверка: грузит модели, синтезирует фразу, распознаёт её обратно, печатает время и занятую видеопамять,
   одним крошечным запросом проверяет Gemini. Если всё хорошо, включает автозапуск и запускает службу.
9. Печатает итог: адрес ноутбука, как смотреть лог, как собрать отчёт.

Служба стартует при входе в систему. Чтобы сервер поднимался при загрузке ещё до входа, выполни один раз
`sudo loginctl enable-linger $USER` (обычно не нужно, установщик только напомнит).

## Каждый день

| Что | Команда |
|---|---|
| Живой лог (после каждой фразы строка `TURN` со временем) | `journalctl --user -u jarvis-server -f` |
| Работает ли | `systemctl --user status jarvis-server` |
| Перезапустить (после правки настроек) | `systemctl --user restart jarvis-server` |
| Задать/сменить ключ Gemini | `./server/set_key.sh` |
| Отчёт для Мирослава (лог, тайминги, nvidia-smi; ключ скрыт) | `./server/report.sh` (файл в `~/jarvis-logs/server-<дата>.txt`) |
| Запуск в терминале для отладки | `./server/run.sh` (службу на это время останавливает) |
| Обновить | `cd jarvis && git pull && ./server/install.sh` (yt-dlp для музыки обновляется при каждом запуске) |
| YouTube перестал отдавать музыку | `./server/update_ytdlp.sh` (перезапускать службу не нужно) |

Загрузка моделей при старте занимает 30-60 секунд. Плата ищет сервер сама (UDP broadcast), если не нашла, адрес можно
задать в консоли платы: `server ws://<адрес ноутбука>:47801/ws`.

`<репозиторий>/.env` (в git не попадает). Приоритет: переменные окружения, `server.env`, `.env`. После правки:

| `JARVIS_DEVICE` | `auto` | `cuda` / `cpu` для всего сразу |
| `JARVIS_TTS_REF_MAX_S` | `6.5` | сколько секунд образца голоса брать (режется по паузе между предложениями) |

## Строка с таймингами

После каждого хода в лог пишется одна строка, например:

```
TURN ok stt_ms=312 llm_first_token_ms=980 first_sentence_ms=1450 tts_first_audio_ms=620 total_to_first_audio_ms=2490 total_turn_ms=8320 audio_s=7.4 | sentences=3 tts_ms=1800 tts_rtf=0.24 underruns=0 max_gap_s=0.00 chars=210 first_split=53 model=gemini-3.5-flash-lite tools=get_time llm_hedge=- llm_conn=reused music=- mode=wake
```

| Поле | Что мерится |
|---|---|
| `stt_ms` | распознавание речи |
| `llm_first_token_ms` | от запроса к ИИ до первого слова ответа |
| `first_sentence_ms` | от запроса к ИИ до готового первого предложения (его уже можно озвучивать) |
| `tts_first_audio_ms` | синтез первого предложения |
| `total_to_first_audio_ms` | от `listen_stop` (кнопку отпустили) до первого кадра звука, ушедшего на плату: то, что чувствует человек |
| `total_turn_ms` | от `listen_stop` до `audio_end` (звук отдаётся по часам, поэтому включает почти всё время речи) |
| `audio_s` | сколько секунд звука отправлено |
| `tts_rtf` | время синтеза / длительность звука (меньше 1 = синтез быстрее речи, предложения успевают) |
| `underruns`, `max_gap_s` | сколько раз и как надолго речь прерывалась, потому что следующее предложение (или второй кусок первого) не успели синтезировать |
| `sentences` | сколько `jarvis_text` ушло на плату (куски разрезанного первого предложения считаются отдельно) |
| `first_split` | длина первого куска в символах, если первое предложение разрезали (раздел «Быстрый первый звук»); `-` = не резали |
| `model` | модель, которая реально отвечала (при хедже и при переходе на запасную после ошибки это та, чей ответ ушёл на плату) |
| `llm_hedge` | запасной запрос (хедж): `-` не запускали (основная успела за порог или хедж выключен) или никто не ответил (`outcome=error`); `primary` запускали, но первой ответила основная; `fallback` первой ответила запасная. Подробнее в разделе «Медленный ИИ: хедж-запросы» |
| `llm_conn` | соединение с Google у первого запроса хода: `new` = на пути хода было рукопожатие TCP+TLS (первая фраза после старта, пауза дольше `JARVIS_LLM_KEEPALIVE_S`, сервер или VPN закрыл соединение, предыдущий ход оборвали на полуслове); `reused` = соединение уже было (держалось в пуле или прогрето на `listen_start`); `-` = неизвестно (mock, подделка). Раздел «Тёплое соединение с Google» |
| `why` | только у `silent(...)`: слова, которыми ИИ объяснил, почему молчит (буквы и `_`, до 40 символов) |
| `music` | музыка после хода: `-` (не играет), `box:playing`, `box:paused` (колонка платы), `laptop:playing`, `laptop:paused` (mpv на ноутбуке). Ключ стоит перед `mode` |
| `mode` | как началась запись: `ptt` (кнопка BOOT), `wake` (слово «Джарвис») или `follow` (продолжение без слова); всегда последний ключ строки |

Итог `outcome`: `ok`, `aborted`, `error`, `empty(...)` (причина в скобках: `short`, `silence`, `no_speech`, `junk` для
выдуманных Whisper фраз, `wake_only` когда сказано только «Джарвис»; только в режиме `follow` ещё `filler` для междометий и
`low_conf` для неуверенного распознавания), `silent(not_addressed)` (только `follow`: ИИ решил, что фраза не к Джарвису; `silent(blocked)`:
Gemini отказался отвечать по безопасности на запись без обращения), `disconnected`. Строки `TURN` собирает `report.sh` вместе с медианой и разбросом;
новые ключи `first_split`, `llm_hedge`, `llm_conn`, `why`, `music` и `mode` ему не мешают (количество ходов по значениям `llm_hedge` и `llm_conn` он
выводит отдельными строками, число молчаливых ходов `silent(...)` тоже).

## Быстрый первый звук: первое предложение двумя кусками

Что чувствует человек, это `total_to_first_audio_ms`: первое слово ИИ плюс синтез ВСЕГО первого предложения. Синтез растёт с длиной
текста (RTX 4050, fp16, 32 шага: предложение на 7,9 с звука синтезируется 2,3 с, на 1,5 с звука 1,2 с; грубо 0,95 с плюс 0,17 с на каждую
секунду звука). Поэтому если первое предложение ответа длиннее `JARVIS_FIRST_CHUNK_MAX_CHARS` (70 символов), сервер режет его на два куска
по естественной паузе, синтезирует и отдаёт сначала короткий первый, а пока он играет, синтезирует остаток.

Правила деления (функция `find_first_cut` в `sentences.py`, чистая, с тестами). Режется только ПЕРВОЕ предложение каждого ответа,
остальные предложения идут как раньше.

| Правило | Как |
|---|---|
| Где | сначала после запятой, `;`, `:` (с пробелом после) или тире; если знаков нет, то перед «который, что, чтобы, а, но, если, когда, пока, хотя, потому что, где, куда...» |
| Размер | первый кусок 25-56 символов и не меньше трёх слов; остаток не короче 18 символов и трёх слов; из подходящих мест берётся самое позднее (первый кусок должен звучать не короче, чем синтезируется остаток) |
| Если до 56-го символа места нет | самое раннее место до 72-го символа, но только когда остаток от 40 символов |
| Не режем | внутри «кавычек» и (скобок), между числами списка («1, 2, 3»), между «то / потому / даже / только» и «что / если», после сокращения с точкой; «Алексей Сергеевич Пушкин родился...» целиком |
| Нет подходящего места | предложение озвучивается целиком (например, «Британские коты обладают выдающейся склонностью смотреть на окружающих с нескрываемым презрением.»: запятых и союзов нет) |

- Субтитры: каждый кусок уходит отдельным `jarvis_text` (плата дописывает их к субтитру, `final:true` только у последнего), видимый
  текст ровно тот же, что без деления («Жил-был один дракон, который сжёг все книги в округе,» + «а потом заскучал и завёл себе дворецкого...»).
  В память разговора и в строку `sentences=` кусок попадает как есть.
- Решение принимается, не дожидаясь конца предложения: как только набралось 87 символов (113, если до 56-го символа места не нашлось), ИИ ещё пишет
  конец, а первый кусок уже синтезируется. От того, как ИИ нарезал поток, результат не зависит (тест на разные нарезки).
- В `TURN` ключ `first_split=53` (длина первого куска), `-` если не резали. Выключить: `JARVIS_FIRST_CHUNK_SPLIT=0`.
- Запятая на конце первого куска остаётся и в тексте для голоса (проверено ниже: без неё не лучше).

## Медленный ИИ: хедж-запросы

Что измерено у Давида (Китай, Gemini через VPN, `gemini-3.5-flash-lite`): вечером `llm_first_token_ms` на многих ходах 8000-11400 мс
(прогрев при старте 7,7-8,6 с), на следующее утро 1400-2000 мс (прогрев 1,4 с). Сама модель при этом не ломалась и ошибок не отдавала,
просто путь до неё то быстрый, то нет, а до 0.3.1 запасная модель пробовалась только после ОШИБКИ и никогда не помогала от медленного ответа.

Как это работает теперь (`GeminiLLM._hedged` в `llm.py`):

1. Запрос уходит на основную модель, как раньше.
2. Если за `JARVIS_LLM_HEDGE_MS` (2500 мс) от начала запроса основная не дала ни слова, тот же запрос параллельно уходит на следующую запасную
   модель (при списке `JARVIS_LLM_FALLBACK` из одной модели это `gemini-3.1-flash-lite`). В лог пишется строка
   `ИИ: gemini-3.5-flash-lite не дала первого слова за 2500 мс, параллельно спрашиваю gemini-3.1-flash-lite`.
3. Кто первой отдал первый кусок, тот и говорит: его ответ идёт дальше потоком как обычно, а вторая цепочка отменяется сразу (её поток
   закрывается, из него больше никто не читает). Лог: `ИИ: хедж: первой ответила запасная (gemini-3.1-flash-lite), первое слово через 3120 мс
   от начала запроса; основная (gemini-3.5-flash-lite): первого слова ещё не было, отменена`. Для проигравшей, если она успела что-то сделать,
   там же её время: «ошибка через 102 мс» или «первое слово через N мс, но позже».
4. Если основная ответила раньше порога, ничего лишнего не происходит: второго запроса нет, квота не тратится. Лишний запрос уходит только
   на ходах, где основная медленнее порога.

Что считается «первым куском»: первый кусок текста ИИ или первый вызов функции (`get_time`), смотря что придёт раньше: модель, которая
сразу просит вызвать функцию, ничего не говоря, тоже выигрывает гонку. «Мысли» модели (thought) куском не считаются.

Что гарантируется:

- **Функция выполняется один раз.** До объявления победителя из каждой цепочки читается ровно один элемент. Выполнение функции происходит только
  после него, поэтому проигравшая цепочка до вызова `get_time` дойти не может; у победителя функции и последующие раунды идут как раньше.
- **Память разговора по победителю.** В историю попадает только то, что реально ушло на плату, то есть ответ победителя. Текст проигравшей
  до сессии не доходит вообще.
- **Ошибки.** Цепочка, упавшая до первого куска, просто выбывает, пока жива другая (её ошибка пишется на уровне debug, а не warning). Если упали
  обе, наружу уходит ошибка той, что упала последней, и плата показывает обычное сообщение. Если победитель упал уже после первого куска (или после
  выполненной функции), повторять поздно: ошибка наружу, как и раньше. Если основная упала с ошибкой раньше порога, хедж не запускается: сразу
  идёт обычный переход на запасную (а если и она к порогу молчит, а в списке за ней есть ещё модель, хедж уйдёт на следующую).
- **Несколько запасных.** Хедж берёт модель, следующую за той, на которой основная цепочка сидит в момент порога; остальные модели списка
  с этого момента принадлежат запасной цепочке, основная на них сама не переходит (иначе две цепочки спрашивали бы одну и ту же модель).
- **Прогрев и проверка связи** (`check-llm`, `selftest`, старт сервера) не хеджируются: они меряют именно основную модель.

Как читать `llm_hedge=` в строке `TURN`:

| Значение | Что произошло |
|---|---|
| `llm_hedge=-` | запасной запрос не запускали: основная успела за порог (норма) или `JARVIS_LLM_HEDGE_MS=0`; также `-` при ошибке, если никто не ответил |
| `llm_hedge=primary` | основная не уложилась в порог, запасной запрос ушёл, но основная всё же ответила первой (порог, возможно, чуть мал: лишний запрос потрачен зря) |
| `llm_hedge=fallback` | основная не уложилась в порог, запасной запрос ушёл и ответил первым; в `model=` запасная модель, `llm_first_token_ms` уже включает порог ожидания |

Читать вместе с `model=` (там модель, которая реально отвечала) и `llm_first_token_ms=` (от запроса к ИИ до первого слова, считая и 2,5 с порога). В
`report.sh` под сводкой теперь строка `llm_hedge: -=..., primary=..., fallback=...` с числом ходов по каждому значению. Если на вечерних ходах
стало много `fallback`, а `llm_first_token_ms` упал с 8-11 с примерно до порога плюс скорость запасной, хедж работает; если `fallback` почти нет, а `-`
везде, хедж ни разу не понадобился. Порог: 2500 мс при обычных 1,4-2,0 с основной оставляет запас от лишних запросов; ниже
(1500-2000) хедж срабатывает чаще и быстрее, но чаще тратит квоту запасной модели; `0` выключает.

### Необязательная заглушка «Секунду, сэр.»

`JARVIS_LLM_FILLER_MS=3000`: если первого слова ИИ всё ещё нет через 3 с, Джарвис говорит «Секунду, сэр.», чтобы не молчать. По умолчанию
выключена (`0`). Заглушка синтезируется один раз при старте сервера (если синтез не удался, пишется предупреждение и заглушки просто нет) и уходит на
плату как обычное предложение (`jarvis_text` со звуком), поэтому прошивка не меняется. Она не попадает в память разговора (чтобы ИИ не перенимал её
как свою манеру) и не считается паузой в речи (`underruns`), а `total_to_first_audio_ms` у такого хода меряет уже её, а не настоящий ответ (смотри
`llm_first_token_ms` и строку лога `ИИ молчит уже ... мс: говорю заглушку`). Если слово от ИИ пришло раньше порога, заглушки не будет. Настоящий
ответ начнётся после того, как заглушка доиграет.

## Режимы разговора: кнопка (ptt), слово «Джарвис» (wake) и продолжение без слова (follow)

Плата v0.4.0 сама ловит слово «Джарвис» (на сервер звук до этого не идёт), после чего шлёт `listen_start` с
`"mode":"wake"`, звук с момента сразу после слова и `listen_stop`, когда услышала 0,8 с тишины (или 5 с без речи, или
прошло 12 с). Для сервера это тот же ход, что и по кнопке: тот же конвейер, те же тайминги. Отличия только такие:

- `mode` попадает в лог (`Вы (wake): ...`) и последним ключом в строку `TURN` (`mode=wake`). Без поля (старые прошивки)
  считается `ptt`. Неизвестное значение не отвергается: сервер пишет в лог предупреждение и ведёт себя как в `ptt`.
- Из распознанного текста снимается обращение в начале фразы, и в ИИ, в субтитр `user_text` и в память разговора
  идёт уже текст без него: «Джарис, ты меня слышишь?» превращается в «Ты меня слышишь?». Исходная фраза остаётся в логе
  строкой `обращение снято`.
- Если после снятия ничего не осталось (человек сказал только «Джарвис» или «Привет, Джарвис», или в запись попал один хвост
  слова), ход заканчивается так же, как при пустой речи: `state idle`, без `user_text`, ответа и обращения к ИИ
  (`TURN empty(wake_only)`).

Что снимается (функция `strip_wake_word` в `textnorm.py`, чистая, с тестами):

| Режим | Снимается в самом начале фразы | Не снимается |
|---|---|---|
| `wake` | имя во всех написаниях Whisper (джарвис, жарвис, джарис, джервис, джарвиз, джарви, дарвис, ярвис, `jarvis`...) с «привет / здравствуй / эй / слушай / ну» перед ним и запятой, тире, двоеточием после; повторы («привет жарвис привет жарвис»); одинокий хвост слова пробуждения «вис», «рвис» | имя внутри фразы («расскажи про Джарвиса»), слова вроде «дарвинизм», «через», «сервис», «вес»; «привет» без имени |
| `ptt` и неизвестные | только имя в самом начале и только если дальше есть слова: «Джарвис, включи свет» -> «Включи свет» | «привет, Джарвис, ...» (оставляется как сказано), текст из одного «Джарвис» (пустым не становится) |

Для обоих режимов: слово-«клик» от кнопки перед обращением («кнопки привет джарвис ...») тоже снимается. После снятия
первая буква делается заглавной (для субтитра).

### Режим follow: продолжение разговора без слова «Джарвис»

После ответа плата ещё около 6 секунд слушает без слова пробуждения (для игры в «города», уточняющих вопросов). Если её детектор речи
(VAD) услышал голос, она шлёт `listen_start` с `"mode":"follow"`, звук с предзаписью ~400 мс и `listen_stop`: для сервера это тот же ход, что и в
`wake`, с такими отличиями:

- `follow` известный режим (предупреждения в логе нет), в строке `TURN` он последний ключ (`mode=follow`).
- В записи ~0,4 с предзаписи (не речь), поэтому «слишком короткой» считается запись, в которой речи меньше 0,3 с сверх них (`JARVIS_FOLLOW_PREROLL_S`).
- Обращение «Джарвис» в начале снимается как в `wake` («Джарвис, который час?» -> «Который час?»), только имя -> пусто.
- Если распознавание пусто, или мусор, или остались одни междометия, или Whisper не уверен: ход кончается молча, как при пустой речи:
  `state thinking` (его плата получает в любом режиме сразу после `listen_stop`), затем `state idle`, без `user_text`, звука, ошибки и
  обращения к ИИ (`TURN empty(...) mode=follow`, ИИ не вызывается и не расходуется).
- В комнате слышно всё подряд (разговор, телевизор, смех), поэтому для `follow`, и только для него, работает лёгкий отсев (`followguard.py`,
  отключается `JARVIS_FOLLOW_GUARD=0`; в `ptt` и `wake` человек сам решил говорить, там он не применяется):

| Проверка | Условие | Итог в логе | Примеры |
|---|---|---|---|
| Уверенность Whisper | средний `avg_logprob` сегментов < `JARVIS_FOLLOW_MIN_LOGPROB` (-1.1) или наибольший `no_speech_prob` > `JARVIS_FOLLOW_MAX_NO_SPEECH` (0.6) | `empty(low_conf)`, строка `follow: отброшено (low_conf): «...» avg_logprob=-1.45` | шум и далёкие голоса, принятые за слова: «Yes, let me», «Джейдс» вместо «который час», «дешкаркова» |
| Междометия и смех | в фразе только слова из перечня (после нижнего регистра, «ё» -> «е», сжатия повторов букв «эээ» -> «э»): «угу, ага, ыгы, хм, гм, эм, мм, мхм, мда, ну, эх, ох, ах, ух, ой, ай, ого, уф, фу, кхм», смех («ха-ха-ха», «хихи», «хехе», «ахаха», «гы-гы»), одна буква | `empty(filler)` | «угу», «Ага.», «Хм...», «Ну, угу», «э-э-э», «ха-ха-ха!» |
| Только имя | после снятия обращения пусто | `empty(wake_only)` | «Джарвис», «Эй, Джарвис» |
| Проходит | всё остальное, в том числе одиночные слова | обычный ответ | «Москва», «Анапа», «да», «нет», «спасибо», «хорошо», «ладно», «пять» и «5», «Ну давай», «Включи свет» |

«Спасибо», «хорошо», «ладно», «да», «нет» намеренно не в перечне: это ответы на вопрос Джарвиса или его слова, а что из дошедшего
относится к Джарвису, решает дальше ИИ (следующий подраздел).

Как подобраны пороги и что они умеют (синтетика: 29 фраз голосом проекта, каждая в пяти условиях: чисто; шум комнаты 15 и 8 дБ; издалека с
реверберацией и шумом 8 и 3 дБ; настоящий `WhisperSTT` large-v3-turbo с теми же настройками, что на сервере; живых записей с платы в выборке нет):

| Что | Дошло до сервера (остальное пусто ещё в распознавании) | `avg_logprob`: min / медиана | Итог при пороге -1.1 |
|---|---|---|---|
| Настоящие слова и фразы вблизи (17 фраз x 3 условия) | 50 из 51 | -1.00 / -0.28 | все 50 проходят (при -0.9 «Казань» в шуме 8 дБ, -1.00, отбрасывалась) |

Выводы, важные для настройки:
- `avg_logprob` не отличает «мне» от «не мне»: чёткая чужая речь Whisper понятна, она получает -0.06...-0.23 и проходит (телевизор в той же комнате ответит
  ИИ). Одиночные настоящие слова получают -0.5 («Да», «Нет», «Спасибо» уже в тишине), поэтому порог жёстче -1.0 начинает резать именно их, а не болтовню.
  Порог убирает только распознанный шум. Различить, к кому обращались, может только ИИ: персона просит переспросить «Это мне, сэр?».
- `no_speech_prob` у любого текста, дошедшего до сервера, 0.00 (его уже срезает VAD распознавания); порог оставлен как страховка.
- Розовый шум комнаты без речи (-50, -35 и -25 дБ, 2 с) уходит пустым ещё в распознавании (`empty(no_speech)`).

### Режим follow: молчать, когда фраза не к Джарвису (0.3.2)

Что было в 0.3.1 (живые записи ноутбука в Китае, окно `follow` 6 с после каждого ответа): сервер отвечал на болтовню в комнате,
потому что чёткую чужую речь Whisper понимает хорошо, а отсев выше срезает только шум и междометия. Не к Джарвису были «Пожалуйста.
Сейчас, замолчи, пожалуйста. ..., Мирик, ..., смотри.» (запись на предельные 12 с), «Why don't you like me? No, I do!» (видео),
«Стрим! Стрим!». К нему были «Пасару нет, ты очень крут, Джарвис.», «Алмата» (игра в города), «Расскажи мне историю».

Как это работает теперь (`addressing.py`, только `follow`, включено `JARVIS_FOLLOW_SILENCE=1`):

1. Фраза прошла отсев (`followguard.py`). Если в ней есть имя «Джарвис» (где угодно и в любом написании Whisper, или его сняли в начале),
   обращение было: ИИ ничего не спрашиваем, ход идёт как в 0.3.1.
2. Иначе в ИИ уходит не голая фраза, а короткая служебная подводка (`follow_prompt`, около 1100 символов) и сама фраза в конце:
   что это запись без слова «Джарвис» (микрофон после ответа ещё слушал комнату), его прошлый ответ, примеры «к тебе» и «не к тебе»
   (из живых записей выше), правило «если идёт игра или беседа с тобой и ты сомневаешься, отвечай» и просьба не переспрашивать
   «Это мне, сэр?» (в `follow` вместо неё теперь решение). В память разговора идёт только сама фраза, без подводки.
3. ИИ либо отвечает как обычно, либо первым в ответе выводит пометку `[SILENT]`, пробел и 2-5 слов причины («чужой разговор»,
   «видео на английском»). Пока по началу ответа не ясно, пометка это или обычный текст, `SilenceGate` держит начало у себя: в озвучку,
   на плату и в субтитр не уходит ни символа. Пометка узнаётся в разных обёртках: `[SILENT]`, `(SILENT)`, `<silent>`, `**[SILENT]**`, строчными и по-русски `[МОЛЧУ]`; без скобки впереди это уже обычный текст.
4. Ответ: как раньше, но `user_text` («Вы: ...») теперь уходит не до запроса к ИИ, а сразу после решения «отвечаю» (то есть с первым
   куском ответа). Молчание: плате уходит только `state idle` (`state thinking` ушёл сразу после `listen_stop`, как в любом ходе),
   без `user_text`, `jarvis_text` и звука. Плата открывает окно `follow` только после ответа со звуком, поэтому молчание кончает цепочку.
   В логе `follow: промолчал (not_addressed): «фраза»; причина: ...`, затем `TURN silent(not_addressed) ... why=чужой_разговор ... mode=follow`.

| Ход | Что видит плата |
|---|---|
| `follow`, ответ | `thinking` → `user_text` → `speaking` → `jarvis_text`/звук → `audio_end` → `idle` |
| `follow`, молчание | `thinking` → `idle` |
| `follow`, в фразе есть «Джарвис», `ptt`, `wake`, `JARVIS_FOLLOW_SILENCE=0` | как в 0.3.1: `thinking` → `user_text` (сразу) → ответ |

Почему пометка в начале текста, а не вызов функции `stay_silent`:

- Решение приходит в том же потоке, что и ответ. Вызов функции в цикле сервера значит `FLUSH`, выполнение и возврат результата модели:
  второй круг к ИИ, на этом канале это ещё 2-4 с, и его пришлось бы обрезать специально.
- У Gemini flash-lite перед вызовом функции бывает текст («Сейчас гляну»). С функцией такое начало фразы ушло бы в озвучку до решения;
  пометка по построению стоит первой, и ничего не уходит, пока она не узнана.
- Обычный ответ не ждёт: если первый непробельный символ не `[`, `<`, `(`, `{`, `*` и не обратная кавычка, весь первый кусок идёт дальше в том же такте. Тест
  `test_gate_stream_first_chunk_does_not_wait_for_the_rest` проверяет, что кусок выходит из ворот, пока остальной поток ещё не пришёл
  (тест допускает до 50 мс, замер на двухкусочном ответе: ворота добавляют около 2 мкс), и сквозной тест, что `first_sentence_ms` с воротами и без отличаются меньше чем на 100 мс.
  Если первый кусок начинается как пометка (`[`, `[SIL`), ждём следующий, обычно миллисекунды; не дольше 40 символов.
- Не сработало в обе стороны безопасно: ИИ забыл пометку, значит, ответ как в 0.3.1; ИИ промолчал зря, значит, один пропущенный ответ
  (человек повторит со словом), поэтому в подводке смещение «сомневаешься во время игры или беседы с тобой: отвечай».
- Просто проверить без сети: пометка и любая нарезка потока на куски (тест перебирает все разбиения пометки на 1-4 куска: ни символа наружу).

Память разговора: молчаливый ход НЕ запоминается. История целиком уходит в ИИ на каждом следующем ходе, и пара «чужая фраза» -
«[SILENT]» учила бы модель (как пример в контексте) молчать чаще и сбивала бы игры («города» идут по чередованию настоящих ходов).
Чужая болтовня не часть диалога и не должна жить в его истории; про неё модели знать не надо. Такой ход не продлевает и срок жизни памяти.
Минус: если человек потом скажет «что?» про то, что было в комнате, Джарвис не поймёт. Это плата за чистую историю.

Что ещё сделано вокруг:

- Заглушка «Секунду, сэр.» (`JARVIS_LLM_FILLER_MS`) в `follow` с воротами не включается: она заговорила бы до решения «молчать».
- Если Gemini отказался отвечать по безопасности (`MSG_SAFETY`) на запись `follow`, это молчание `silent(blocked)`, а не `state error`:
  мат в разговоре соседей не повод показывать ошибку на лице. В `ptt` и `wake` это по-прежнему ошибка.
- Если ИИ упал или вернул пустоту до решения, `user_text` всё равно уходит, потом `state error`, как в 0.3.1.
- Функции (`get_time`) в `follow` работают как раньше: ИИ, который сразу зовёт функцию, этим тоже решает «отвечаю».
- Лог по-прежнему содержит распознанные фразы, в том числе молчаливые («Вы (follow): ...», «follow: промолчал ...»). Фраза уходит в
  Google, как и раньше уходила в `follow`; в историю разговора, а значит и в следующие запросы, она не попадает.

Настройка и проверка:

- Весь текст подводки и пометка в одном месте: `addressing.py` (`follow_prompt`, `MARKER`). Подводка не в `persona.py`: она нужна только в `follow`,
  а персона едет в каждом запросе.
- Решает модель, а не пороги, и на настоящем Gemini это здесь не проверялось (квота ключа Давида). Тесты идут на подделке ИИ: они
  доказывают поведение сервера (ничего не утекает, память, `TURN`), а не точность модели. Для проверки модели есть
  `server/tools/follow_silence_eval.py`: по умолчанию ничего не отправляет (печатает план), с `--yes` делает 12 запросов (по одному на
  фразу: 6 «не к Джарвису» и 6 «к Джарвису», в том числе живые записи выше) и печатает решение, причину и время до решения.
- Температура ИИ общая на все ответы (`JARVIS_LLM_TEMPERATURE`, 0,8): решение «молчать» в `follow` может «плавать». Если на живых ходах
  видно, что молчит зря, сначала смотреть `why=` в `TURN`, потом править подводку.
- Выключить совсем: `JARVIS_FOLLOW_SILENCE=0` и перезапуск.

## Тёплое соединение с Google (0.3.2)

Что нашлось в `google-genai 3.4.0` (окружение из `requirements.lock`) про соединение с Gemini:

- aiohttp в окружении нет (`has_aiohttp` ложно, `_use_aiohttp()` ложно, `_api_client.py:1863`), поэтому потоковый запрос идёт через
  httpx: ветка «aiohttp is not available. Fall back to httpx» (`_api_client.py:2231`).
- Какой httpx: по умолчанию `httpx2` (`_DEFAULT_HTTP_CLIENT_BACKEND = 'httpx2'`, `_api_client.py:1031`), класс `AsyncHttpx2Client` с пулом «по
  клиенту на цикл событий» (`_api_client.py:857-1008`, внутренний клиент строится в `_client_for_running_loop`, `:887`, из тех же аргументов).
- Аргументы клиента (`_maybe_set`, `_api_client.py:1712-1715`) добавляют только проверку сертификатов и `timeout=None`. Лимитов нет, значит
  действуют лимиты httpx2: `Limits.keepalive_expiry = 5.0` и `DEFAULT_LIMITS = Limits(max_connections=100, max_keepalive_connections=20)`
  (`httpx2/_config.py:168`, `:213`).
- Как пул это применяет (`httpcore2`): когда ответ дочитан, у соединения ставится срок жизни `now + keepalive_expiry` (`_async/http11.py:224-226`),
  а проверка ленивая: соединение закрывается, когда пришёл следующий запрос и срок вышел (`_async/connection_pool.py:286`, `has_expired()`
  в `http11.py:255-269`, которая ещё и смотрит, не закрыл ли соединение сервер). Значит, ход через 5 с и больше после предыдущего
  открывал новое соединение TCP+TLS, а через VPN это 0,5-1,5 с к первому слову на каждой фразе после паузы. Проверено на подделке сервера
  (настоящий SDK, `base_url` на localhost): три хода с паузой 6 с дали три соединения, при `keepalive_expiry=120` одно.

Что сделано (`llmconn.py`, `GeminiLLM._client` в `llm.py`):

- В SDK передаётся свой клиент httpx штатным полем `HttpOptions(httpx_async_client=...)`: `Limits(max_keepalive_connections=8,
  keepalive_expiry=JARVIS_LLM_KEEPALIVE_S)` (120 с), без таймаута по умолчанию, редиректы разрешены, проверка сертификатов штатная
  (`SSL_CERT_FILE` и `SSL_CERT_DIR` уважаются; прокси из окружения, `HTTPS_PROXY`, работают как раньше). Один пул на оба бэкенда
  (`gemini` и `vertex`). Побочный эффект: SDK с этим полем не выбирает aiohttp, даже если его кто-то доустановит, транспорт предсказуем.
  SDK чужой клиент не закрывает, `GeminiLLM.aclose()` закрывает его сам.
- `JARVIS_LLM_KEEPALIVE_S=0` возвращает штатный клиент SDK (5 с), как в 0.3.1.
- Прогрев (`JARVIS_LLM_PREWARM=1`): на `listen_start` любого режима, если в пуле нет простаивающего живого соединения (пул
  разглядывается через `connections`, `is_idle()`, `has_expired()`; если разглядеть не вышло, считается живым, когда последний ответ был
  меньше 20 с назад), в фоне уходит `HEAD` на корень хоста (`https://generativelanguage.googleapis.com/`, для Vertex express `https://aiplatform.googleapis.com/`).
  Без ключа, без тела, редиректы не идут: квота генерации не тратится, а соединение остаётся в пуле для запроса хода. Запись и распознавание
  занимают секунды, рукопожатие успевает в это время. Один прогрев за раз, после неудачи (нет VPN) десять секунд заново не пробует,
  ошибки прогрева только в debug. До первого обращения к ИИ (клиент ещё не создан) и без ключа прогрева нет. В логе при новом соединении
  `ИИ: соединение открыто за 640 мс (прогрев на listen_start, HTTP 404)`: это и есть цена рукопожатия на этом канале.
- `llm_conn=new|reused` в `TURN`: определяется в ответе клиента httpx по объекту сетевого потока (один на соединение), у хеджа считается по
  цепочке-победителю. Прогретое соединение даёт `reused`. Если после прогрева на ходе всё равно `new`, Google закрыл соединение на HEAD
  или оно не дожило: тогда `JARVIS_LLM_PREWARM=0`.
- HTTP/2 (`JARVIS_LLM_HTTP2=1`) включается только при установленном `h2`; по умолчанию выключено. Его плюс: обрыв потока (abort, проигравший хедж,
  молчаливый ход) закрывает один поток, а не соединение. Минус: `h2` нет в `requirements.lock`, и на живом Google с VPN это не проверялось.

Что стоит знать:

- Пока поток ответа не дочитан до конца, соединение HTTP/1.1 в пул не возвращается: после `abort`, после проигравшей цепочки хеджа и
  после молчаливого хода, поток которого пришлось закрыть (причину дочитываем до 0,8 с, обычно поток кончается сам), следующий ход
  платит рукопожатием (`llm_conn=new`), если не успел прогрев на `listen_start`.
- Если NAT или VPN-узел молча сбросит соединение между ходами (сервер этого не заметит, FIN не придёт), первый запрос на нём зависнет, пока
  хедж через 2,5 с не откроет второе. TCP keepalive на сокетах не включён: для этого нужен свой транспорт httpx, а он выключает прокси из
  окружения. Срок `JARVIS_LLM_KEEPALIVE_S=120` выбран как компромисс; на живом канале не проверен, смотри долю `new` и `llm_first_token_ms` в отчёте.
- Проверено на подделке сервера на localhost (HTTP и HTTPS с самоподписанным сертификатом, паузы, закрытие соединения сервером, прогрев): на Google
  с VPN ничего из этого не запускалось, нужные цифры даст `report.sh` (строка `llm_conn` и медиана `llm_first_token_ms`).

## Как реализован протокол

- Поиск: UDP-ответчик на порту 47800, в ответе IP того интерфейса, на который пришёл запрос (`IP_PKTINFO`).
  Отвечает только отправителям из частных сетей.
- WebSocket `/ws` на 47801, один разговор за раз: новое подключение вытесняет старое. Подключения не из локальной сети
  получают 403. Свои пинги на уровне WebSocket (каждые 20 с) плюс прикладные `ping`/`pong`: `pong` уходит сразу, даже
  когда идёт генерация ответа.
- Ход: `state thinking` → `user_text` → `state speaking` → `jarvis_text` + `audio_start` + кадры по 40 мс → … →
  `audio_end` → `state idle`. В `follow` (0.3.2) `user_text` ждёт решения ИИ «отвечать или молчать» и уходит с первым куском ответа; если
  ИИ решил молчать, ход кончается `state idle` без `user_text`. `audio_start.rate` всегда 24000. Каждое `jarvis_text` не длиннее 450 символов.
- Субтитр: `jarvis_text` предложения N+1 уходит, когда в буфере платы остаётся не больше `JARVIS_SUBTITLE_LEAD_S` (0,4 с)
  звука предыдущего предложения, то есть почти в момент, когда зазвучит его звук. Последнее предложение идёт с `final:true`;
  если ИИ закончил без нового предложения (например, замолчал после вызова функции), сервер добавляет пустое
  `{"type":"jarvis_text","text":"","final":true}`.
- Подача звука: первые 0,5 с сразу, затем быстрее реального времени вдвое, пока опережение не дойдёт до 1,5 с, дальше
  по часам. Пока плата проигрывает предложение, следующее уже синтезируется. Если оно не успело, плата проигрывает
  тишину (в лог: «пауза в речи»).
- `abort`: отмена всего (ИИ, очередь озвучки, отправка), ответ `audio_end` (если звук шёл) и всегда `state idle`.
  Новый `listen_start` во время ответа тоже отменяет ответ, но молча: плата сама знает, что слушает.
- Перебить Джарвиса голосом (barge-in): пока он говорит и думает, плата слушает слово «Джарвис» и, услышав, шлёт `abort`, сразу следом
  `listen_start` (`wake`) и звук, не дожидаясь ответа на `abort`. Сервер к этому готов: ход отменяется за миллисекунды, а синтез
  на видеокарте прерывается на ближайшем шаге диффузии. Раньше поток синтеза (он один) досчитывал уже ненужную фразу до конца, и следующий
  ответ ждал её. Замер на настоящем OmniVoice (GTX 1650, 32 шага, фраза в 138 символов, `abort` через 1 с после начала синтеза): новая
  фраза («Да.», её собственный синтез 9,1 с) была готова через 28,8 с без отмены и через 10,1 с с отменой, то есть поток освободился за
  один шаг модели (~1 с на этой карте; на RTX 4050 шаг порядка 0,05-0,07 с, а целая фраза до 2,3 с). После подтверждения (`audio_end` + `state idle`) от старого хода не приходит ни кадра звука, ни текста,
  запись после `abort` обрабатывается как обычная (тесты `test_bargein_*`, `test_abort_interrupts_tts_synthesis_in_the_worker_thread`).
  Не прерывается только распознавание речи (Whisper отрабатывает свои доли секунды): `abort` посреди STT и тут же новая запись значит, что
  новое распознавание начнётся после прерванного. Отмена ещё и помечает ход (`ctx.cancelled`) до того, как она дойдёт до дочерних задач:
  в этот короткий промежуток звук и текст уже не уходят.
- Обрыв связи с платой посреди хода отменяет ход.
- Музыка (PROTOCOL §10, плата v0.6.0): в `hello` плата пишет `caps:["music"]`; сервер сам раскодирует трек и шлёт PCM по часам (1 с сразу, дальше не больше
  чем на 2 с вперёд). На `listen_start` кадры музыки перестают идти, а после КАЖДОГО хода (ответ, молчание, пустая запись, ошибка) уходит ровно одно из
  `music_resume` / `music_pause` / `music_stop` / `music_start` (`Session._music_turn_end`); `music_start` нового трека только после `audio_end` и
  `state idle`. `abort` посреди хода значит «замолчи»: после `state idle` сервер ждёт 1 с, и если `listen_start` (перебивание словом) не пришёл, шлёт `music_resume`; `abort` без хода
  (короткое BOOT посреди музыки) останавливает музыку, обрыв связи тоже. Раздел «Музыка».
- Ошибки: `state error` с короткой русской подсказкой (нет связи с ИИ/VPN, ключ, лимит запросов, перегрузка, сбой
  голоса). После `error` сервер `idle` не шлёт: плата сама решает, когда вернуть лицо.
- Запись короче 0,3 с речи (плюс ~0,2 с «до-записи», которую плата добавляет в начало; в режиме `follow` ~0,4 с) сразу даёт
  `state idle` без ответа. Тишина и мусор распознавания тоже кончаются на `idle`.

## Характер Джарвиса и память разговора

Характер задаёт `server/jarvis_server/persona.py` (системная инструкция для Gemini). Что в ней важно для голоса:

- Ответы короткие: обычно одно-два предложения, длиннее только по просьбе. Первое предложение до 10-12 слов и без цепочки придаточных
  (так оно не попадает под деление из раздела «Быстрый первый звук» и первый звук ещё раньше).
- Джарвис никогда не произносит своё имя «Джарвис» в ответах: пока он говорит, плата слушает это слово, и услышав его из собственного
  динамика, оборвала бы сама себя. На вопрос «как тебя зовут?» он отвечает без имени («Ваш помощник, сэр»). Запасная защита на случай, если ИИ
  всё же назвался: `mute_own_name` (`textnorm.py`) заменяет имя в тексте для синтезатора на «ваш помощник» (субтитр остаётся как написал ИИ),
  в логе строка «ИИ назвал себя по имени».
- Разговор можно продолжать без слова «Джарвис» (режим `follow`): это следующая реплика, не новое знакомство. Если непонятно, мне ли сказано,
  он переспрашивает «Это мне, сэр?».
- Игры («города», слова, загадки) ведутся по памяти разговора: за ход один город и сразу «Вам на А» (последняя буква, кроме ь, ъ, ы, й).
  Поэтому память по умолчанию 20 последних обменов (`JARVIS_MEMORY_TURNS`; было 10, а в игре обменов много и короткие). История уходит в
  Gemini целиком, на скорость ответа почти не влияет.

Живая проверка на `gemini-3.5-flash-lite` (скрипт не в репозитории; старая и новая инструкция, по одному запросу на вариант):
- Имя, 6 вопросов («как тебя зовут?», «скажи своё имя», «повтори пять раз слово Джарвис», «кто ты?», «Привет, Джарвис! Ты тут?», «Меня зовут Давид,
  а тебя?»): старая инструкция называла имя в 5 ответах (кроме «Привет, Джарвис!»), новая в 0 («Ваш помощник, сэр», «Это слово меня перебивает, сэр»).
- Длина: на 8 открытых вопросов первое предложение в среднем 87 символов → 72 (максимум 131 → 93), весь ответ 192 → 156 символов. Первое
  предложение дольше 70 символов осталось в 5 ответах из 8, так что деление из раздела «Быстрый первый звук» по-прежнему нужно.
- Игра в «города» с памятью 20 обменов: 16 ходов подряд без ошибок (город на нужную букву, без повторов, «Вам на К, сэр» с верной буквой
  с учётом ь, ъ, ы, й), ответ из 3-4 слов. Выборка маленькая, не гарантия: если ИИ нарушит запрет на имя, сработает защита выше.

## Управление ноутбуком (Hyprland)

Джарвис умеет делать дела на ноутбуке, на котором работает сервер: открывать программы, переключать окна, менять громкость, включать
паузу, открывать сайты, блокировать экран, а с подтверждением и выключать. Это громкость и экран **ноутбука**, а не колонки в коробочке
Джарвиса. Работает в сеансе Hyprland, для остальных рабочих столов функции просто не появляются.

### Что можно сказать

| Фраза | Функция (ИИ вызывает её сам) |
|---|---|
| «Открой телеграм», «запусти браузер», «открой терминал / стим / файлы / дискорд / спотифай / код» | `open_app` |
| «Переключись на телеграм», «покажи браузер» | `focus_window` |
| «Закрой окно», «на весь экран» | `close_active_window`, `toggle_fullscreen` |
| «Перейди на третий рабочий стол», «перенеси окно на пятый» | `go_to_workspace`, `move_window_to_workspace` (1-10) |
| «Сделай громче», «громкость на тридцать», «выключи звук» | `volume_control` (get, set, up, down, mute, unmute, toggle_mute; не выше 100) |
| «Поставь на паузу», «следующий трек», «что сейчас играет?» | `media_control` (play_pause, play, pause, next, previous, stop, status) |
| «Сделай ярче», «яркость пятьдесят» | `brightness_control` (get, set, up, down) |
| «Открой youtube.com», «найди в интернете рецепт борща», «найди на ютубе...» | `open_website`, `web_search` (google, yandex, duckduckgo, youtube, wikipedia) |
| «Заблокируй экран» | `lock_screen` |
| «Выключи ноутбук», «перезагрузи», «усыпи» | `power_action` и `confirm_pending_action` (см. ниже) |

Каждая функция возвращает короткий ответ `{"ok": true, ...}` или `{"ok": false, "error": "<код>", "message": "..."}`; по нему Джарвис
говорит «Открыл Телеграм, сэр» или «На ноутбуке нет playerctl». Коды ошибок: `bad_argument`, `not_found`, `ambiguous` (подходит несколько:
в `candidates` варианты, Джарвис спросит, какой), `tool_missing` (нет программы), `no_player`, `timeout`, `hyprland_refused`, `no_hyprland`,
`rate_limited`, `needs_confirmation`. У запуска программы `ok` значит «команда отправлена в Hyprland», окно появится через пару секунд.

Как называют программы: индекс строится из файлов `.desktop` (`/usr/share/applications`, `~/.local/share/applications`, остальные
каталоги `XDG_DATA_DIRS`, экспорты flatpak и snap) по `Name`, `Name[ru]`, `GenericName`, `Keywords`, `StartupWMClass`, имени программы из
`Exec`. «Телеграм», «дискорд», «спотифай», «стим» сопоставляются с английскими названиями по звучанию, «браузер», «терминал», «файлы»
означают программу такой категории (если браузеров несколько, берётся тот, что стоит по умолчанию в `mimeapps.list`, иначе Джарвис
спрашивает). Своё прозвище программе дописывают в `ALIASES` в `server/jarvis_server/skills/pc/apps.py`. Запустить можно только то,
что есть в индексе; игры Steam и прочие ярлыки в нём тоже есть. Список обновляется сам, когда ставят программу.

### Как найти Hyprland из службы

У пользовательской службы systemd нет `HYPRLAND_INSTANCE_SIGNATURE` и `WAYLAND_DISPLAY`, поэтому сервер ищет сеанс сам:

1. Просматривает `$XDG_RUNTIME_DIR/hypr/<подпись>/`. Подпись `<коммит>_<unix-время>_<число>`, по времени берётся самый свежий сеанс.
2. «Живой» сеанс: в `hyprland.lock` указан существующий процесс, к `.socket.sock` удаётся подключиться, а
   `hyprctl --instance <подпись> version` отвечает. Каталоги после упавшего Hyprland остаются, такие пропускаются.
3. Команды идут как `hyprctl --instance <подпись> ...`. Программы запускаются через `hyprctl dispatch exec`, поэтому получают окружение
   самого Hyprland (Wayland, `PATH` пользователя) и не привязаны к службе: перезапуск `jarvis-server` их не закрывает.
4. Если Hyprland перезапустили, сервер находит новый сеанс сам. Если сеанса нет (вход ещё не выполнен), функции управления просто не видны
   ИИ, а в инструкцию не добавляется блок о них; как только Hyprland появится, они включаются без перезапуска сервера.
5. `wpctl`, `playerctl` и остальное запускаются с `XDG_RUNTIME_DIR` (у службы он есть) и `DBUS_SESSION_BUS_ADDRESS` (его ставит `dbus.socket`;
   если не задан, сервер подставляет `unix:path=$XDG_RUNTIME_DIR/bus`).

**Две «грамматики» `hyprctl dispatch`.** С конфигом `hyprland.conf` команда выглядит `dispatch exec firefox`, с новым Lua-конфигом
(`hyprland.lua`, у такого Hyprland есть `hyprctl eval`) `dispatch` принимает Lua-выражение: `dispatch 'hl.dsp.exec_cmd("firefox")'`. Сервер
определяет, какая из них у работающего сеанса, безвредной пробой `hyprctl eval "return 1"`, а если команда не принята, один раз пробует вторую
(чужая грамматика даёт ошибку разбора и ничего не делает). Принудительно: `JARVIS_PC_HYPR_DIALECT=legacy` или `lua` в `server.env`.

### Подтверждение выключения

Выключение, перезагрузка и сон никогда не выполняются из одной реплики:

1. «Выключи ноутбук»: Джарвис вызывает `power_action`. Она ничего не делает, а запоминает действие на **20 секунд** и отвечает
   `needs_confirmation`. Джарвис спрашивает «Точно выключить, сэр?».
2. Человек отвечает в **следующей реплике**: у платы после ответа 6 секунд слушает режим follow, слово «Джарвис» не нужно. «Да»,
   «подтверждаю», «давай», «да, выключай» это согласие; «нет», «стоп», вопрос, другая просьба, невнятица, молчание дольше 20 секунд
   это отмена.
3. Сервер сам сверяет слова человека (то, что распознал Whisper) с перечнем согласий; Gemini на это повлиять не может. Только после этого
   `confirm_pending_action` выполняет `systemctl poweroff|reboot|suspend`. Вызванная в той же реплике, где просили выключить, она ничего не делает.
4. После подтверждения действие откладывается на 4 секунды, чтобы Джарвис успел сказать «Выключаю». «Нет» или «стоп» за эти секунды отменяет.

Подтверждение опирается на вызов `registry.begin_turn(текст)` в начале каждого хода (`Session._answer`). Если его потерять, подтвердить будет нечем и
питание не сработает никогда (тест `test_session_power_needs_a_second_utterance_with_yes` это проверяет).

### Безопасность и приватность

- Нет произвольных команд: каждая функция собирает фиксированный список аргументов (`subprocess` без shell, с таймаутом) из проверенных данных.
  Программу можно открыть только из индекса, адрес только `http`/`https` без логина и пробелов, рабочий стол 1-10, громкость 0-100
  (и `-l 1.0` у `wpctl`), яркость 1-100. Командная строка для `hyprctl dispatch exec` собирается через `shlex.join`, для Lua через экранирование.
- Каждое выполненное действие пишется в журнал на INFO (`ПК: open_app {...} -> ok ...`, источник `jarvis.pc`). Одинаковое действие с теми же
  аргументами в течение 2,5 с повторно не выполняется (ответ `duplicate_ignored`), всего не больше 20 действий за 10 секунд.
- К Google уходят ответы функций: названия программ, классы окон (`firefox`, `org.telegram.desktop`), громкость, название и исполнитель
  трека (когда спрашивают «что играет» или переключают трек). **Заголовки окон** ИИ не получает.

### Как выключить

В `~/.config/jarvis/server.env` строка `JARVIS_PC_CONTROL=0`, затем `systemctl --user restart jarvis-server`. Функции и блок в инструкции ИИ
не подключаются совсем. `python -m jarvis_server check-pc` показывает состояние (найден ли сеанс, какая грамматика, какие программы есть,
сколько приложений в индексе); команду запускай из терминала Hyprland. Её же вызывает `./server/install.sh` в итоговой сводке.

### Если не работает

| Симптом | Что делать |
|---|---|
| Джарвис говорит, что не умеет управлять ноутбуком; в строке `TURN` нет `tools=` | `python -m jarvis_server check-pc` из терминала Hyprland. В журнале при старте: `управление ПК: функции подключены` или причина (`hyprctl не найден`, `выключено`) |
| «Сеанс Hyprland не найден» из службы, а в терминале всё работает | `ls $XDG_RUNTIME_DIR/hypr/` и `hyprctl instances`; служба должна работать под тем же пользователем, что и Hyprland (`systemctl --user`, не `sudo`). Если Hyprland стартует после входа, подожди: сервер подхватит его сам. Устаревшие каталоги от упавшего Hyprland он пропускает |
| `hyprland_refused` («Hyprland не принял команду») | чаще всего грамматика `dispatch`: выставь `JARVIS_PC_HYPR_DIALECT=lua` (конфиг `hyprland.lua`) или `legacy` (`hyprland.conf`); руками: `hyprctl dispatch 'hl.dsp.window.close()'` или `hyprctl dispatch killactive`. Подробности в журнале: `hyprctl dispatch (...) не принят: ...` |
| «На ноутбуке нет playerctl» (`tool_missing`) | `sudo pacman -S --needed playerctl`; `./server/install.sh` предложит сам. То же для `wpctl` (пакет `wireplumber`) и `brightnessctl` |
| «Сейчас нет ни одного плеера» (`no_player`) | плеер должен поддерживать MPRIS (Spotify, VLC, браузеры). `playerctl -l` покажет, что видно. Если пусто только из службы, проверь `DBUS_SESSION_BUS_ADDRESS` |
| Громкость не меняется | `wpctl get-volume @DEFAULT_AUDIO_SINK@` в терминале; из службы нужен `XDG_RUNTIME_DIR` (есть всегда) |
| Программа не находится (`not_found`) | у неё должен быть файл `.desktop`; поищи `grep -ril имя /usr/share/applications ~/.local/share/applications`. Прозвище добавляют в `ALIASES` (`skills/pc/apps.py`) |
| Джарвис не выключает после «да» | в журнале `питание: ...`: `истекло 20 секунд` (ответил слишком поздно), `следующая реплика не согласие` (распознано не «да»; проверь строку «Вы (follow): ...») |
| Лишнее срабатывание | `JARVIS_PC_CONTROL=0` отключает всё; журнал `journalctl --user -u jarvis-server -g "ПК:"` показывает каждое действие |

## Музыка

Джарвис включает музыку по просьбе. **По умолчанию она играет из динамика коробочки** (колонки платы), а если сказать «на компе», «на ноутбуке» или
«на компьютере», то на самом ноутбуке.

### Что можно сказать

| Фраза | Что происходит |
|---|---|
| «Включи Capsize Ты любишь танцевать» | поиск на YouTube, трек играет в колонке |
| «Включи что-нибудь из Capsize», «поставь группу Кино» | очередь до 10 треков (`kind=artist`), работает «следующий» |
| «Включи на компе Кино Группа крови» | то же на ноутбуке (mpv) |
| «Включи на саундклауде …» | поиск на SoundCloud вместо YouTube |
| «Найди у меня на компе файл Ты любишь танцевать и включи» | поиск аудиофайла на ноутбуке (`source=local`); играет в колонке, а «найди … и включи на компе» на ноутбуке |
| «Пауза», «продолжи», «стоп», «следующий», «предыдущий» | управление тем, что включено; «продолжи» после «стоп» включает с того же места |
| «Громче», «тише», «громкость сорок» | громкость музыки (на колонке шаг 15 из 100, громкость самого голоса не меняется) |
| «Что сейчас играет?» | название, место в очереди |

Если по названию подходит несколько файлов («Танцы (live)» и «Танцы (studio)»), Джарвис называет варианты и спрашивает. Если плата с прошивкой
старше v0.6.0 (в `hello` нет `caps` с `music`), музыка идёт на ноутбуке, и Джарвис честно говорит, что колонка пока не умеет. Spotify и Яндекс Музыку
так включить нельзя (нет открытого потока); ими, как и музыкой в браузере, управляют старые функции `media_control` и `volume_control` (раздел про
управление ноутбуком), а `music_control` отвечает только за то, что включила `play_music`.

### Как это устроено

Две функции для ИИ (`skills/music/`): `play_music(query, where=box|laptop, source=auto|youtube|soundcloud|local, kind=track|artist)` и
`music_control(action=pause|resume|stop|next|previous|volume_up|volume_down|set_volume|status, percent)`. Результат это `{"ok": true, ...}`
или `{"ok": false, "error": код, "message": по-русски}`; `ok=true` у `play_music` значит, что звук **реально пошёл**: у колонки раскодированы
первые отсчёты, у ноутбука mpv начал играть (его свойства `core-idle=false` и `time-pos` по IPC), а не «команда отправлена». Ждать дольше
`JARVIS_MUSIC_START_TIMEOUT` (20 с) не будем. Коды ошибок: `not_found`, `ambiguous`, `network`, `no_ytdlp`, `no_ffmpeg`, `no_mpv`, `no_js_runtime`,
`blocked`, `forbidden`, `unavailable`, `timeout`, `no_board`, `nothing_playing`, `no_next`, `no_previous`. Блок инструкции ИИ (`skills/music/prompt.py`)
подключается, только пока на ноутбуке есть хоть что-то для музыки (yt-dlp, mpv или ffmpeg).

**Колонка платы.** Сервер делает всё сам, плата получает готовый звук, как голос:

```
поиск: yt-dlp --flat-playlist ytsearch5:запрос    (1-3 с, метаданные, ничего не скачивается)
поток: yt-dlp -f bestaudio -o -  |  ffmpeg -i pipe:0 -f s16le -ac 1 -ar 24000 pipe:1   -->  кадры по 40 мс на плату
```

На YouTube поток первого результата (`yt-dlp ... ytsearch1:запрос | ffmpeg`) стартует одновременно с поиском. Когда поиск вернул список, выбор лучшего трека
(порядок YouTube с поправками, раздел «Ограничения») сравнивается с роликом, который взял yt-dlp (он пишет его id в stderr через ~1,8 с): совпало, значит
этот поток уже разбирает ролик, второй раз разбирать не нужно; не совпало, поток закрывается и идёт обычный путь.

Что и в каком порядке уходит плате, описывает PROTOCOL §10 (`music_start`, `music_title`, `music_pause`, `music_resume`, `music_volume`, `music_stop`,
`music_end`, от платы `music_done`). Что важно для серверной стороны:

- Кадры идут по часам: первая секунда сразу, дальше не больше чем на 2 с вперёд (тот же `AudioPacer`, что у голоса, с `hold()` и `restore()` на время
  паузы платы). Кадры музыки никогда не идут внутри `audio_start`…`audio_end`: на `listen_start` плеер замолкает, и весь ход (запись, распознавание,
  ответ) молчит.
- После каждого хода плата ждёт ровно одно сообщение: `music_resume` по умолчанию; `music_pause`, если человек раньше сам поставил паузу или попросил её
  в этом ходе; `music_stop`, если просили остановить; `music_start`, если включили новый трек (так же «следующий», «предыдущий» и «продолжи» после стопа:
  начинается другой звук, плата выбрасывает буфер). Функции хода только записывают намерение, а сообщение уходит после `state idle` ответа, поэтому «Включаю,
  сэр» не перебивается музыкой. Новый трек раскодируется уже во время хода (первые полсекунды читаются заранее), и музыка начинается без паузы.
- Сервер держит позицию (сколько отсчётов отправил) и очередь. Если поток умер посреди трека (сеть, yt-dlp упал), он открывается заново с этого места
  (`ffmpeg -ss` выбрасывает начало; до двух раз подряд). Если пауза или разговор длились дольше минуты, поток тоже открывается заново с позиции перед
  продолжением (сеть за это время могла его закрыть). На паузе сервер ничего не читает: канал между yt-dlp и ffmpeg заполняется, и они засыпают.
  Следующий трек очереди запускается за 15 секунд до конца текущего, на стыке плата получает только `music_title`, без паузы.
- `abort` посреди хода (короткое BOOT во время ответа, слово «Джарвис» посреди ответа) значит «замолчи», а не «выключи музыку»: плата музыку не трогает, после
  `state idle` сервер ждёт 1 с (`abort_grace_s`). Пришёл `listen_start` (перебивание): про музыку ни слова, новый ход кончится своим одним сообщением. Не пришёл: `music_resume`
  (или то, что решили функции прерванного хода: «включи X» и BOOT посреди «Включаю, сэр» всё равно включит X). `abort` без хода (короткое BOOT посреди музыки или на её паузе,
  плата уже сама почистила буфер) останавливает музыку и запоминает место: «продолжи» включит её с него (полчаса). Обрыв связи с платой тоже останавливает музыку;
  после нового `hello` она сама не включается. Окно `follow` в режиме музыки плата не открывает.
- Если ffmpeg в системе нет, звук раскодирует запасной PyAV (пакет `av` уже стоит из-за faster-whisper): колонка играет, хотя ffmpeg надёжнее.

**Ноутбук.** mpv запускается в фоне без окна и видео (`--no-video --vo=null`) с IPC-сокетом `$XDG_RUNTIME_DIR/jarvis-mpv.sock`; очередь это плейлист mpv
(`playlist-next`, `playlist-prev`), управление идёт по сокету. Для YouTube mpv вызывает yt-dlp из окружения сервера (`--script-opts=ytdl_hook-ytdl_path=...`),
а не системный. Если установлен `mpv-mpris`, mpv виден для `playerctl`, и `media_control` тоже может им управлять. Пока идёт ход разговора (с `listen_start`
до конца ответа), громкость mpv приглушается до 30% от обычной и потом возвращается (иначе плата не расслышит слово, а голос потонет). Громкость
музыки на ноутбуке это громкость самого mpv (по умолчанию 100), общую громкость ноутбука меняет `volume_control`. `abort` платы музыку на ноутбуке не останавливает; приглушение снимается так же, как продолжается музыка колонки: через 1 с после `abort` посреди хода, если не пришёл `listen_start`.

**Файлы на ноутбуке.** Каталоги: `JARVIS_MUSIC_DIRS`, `XDG_MUSIC_DIR`, `~/Music`, `~/Музыка`, затем `~/Downloads`, `~/Загрузки`, `~/Desktop`,
`~/Рабочий стол` и домашняя папка на глубину 2; скрытые каталоги пропускаются, поиск ограничен 3 секундами и 40 тысячами записей. Форматы: mp3, flac, m4a,
ogg, opus, wav, aac. Совпадение нечёткое: регистр, ё/е, знаки препинания, опечатки распознавания («Капсайз» ~ Cupsize) не мешают; слова названия файла
важнее слов папки (папка обычно исполнитель).

### Что нужно установить

Установщик (`./server/install.sh`) предлагает всё сам; необязательное его не валит. Руками:

```
sudo pacman -S --needed ffmpeg deno mpv mpv-mpris      # ffmpeg: звук на колонку; deno: чтобы открылся YouTube; mpv и mpv-mpris: музыка на ноутбуке
./server/update_ytdlp.sh                               # свежий yt-dlp[default] (с yt-dlp-ejs) в окружение сервера
python -m jarvis_server check-music                    # что нашлось и чего нет (как check-pc); то же печатают install.sh и update_ytdlp.sh
```

С конца 2025 года yt-dlp для YouTube нужен **внешний JavaScript-рантайм** (рекомендован deno 2.3+, подходят node 22+, quickjs, bun) и пакет `yt-dlp-ejs`
(решатель, ставится вместе с `yt-dlp[default]`). Без них поиск работает, а воспроизведение нет (`no_js_runtime`). Сервер сам находит рантайм и передаёт его
yt-dlp (`--js-runtimes deno:/usr/bin/deno`).

**Почему yt-dlp не в `requirements.lock`.** YouTube меняется каждые несколько недель, и закреплённая версия за пару месяцев перестаёт открывать треки
(на живой проверке версия 2026.06.09 в ноябре возвращала `HTTP Error 403`, а свежая 2026.10.26 играла). Остальные библиотеки закреплены ради воспроизводимости,
а у yt-dlp ценность как раз в свежести. Поэтому `install.sh` и `update_ytdlp.sh` каждый раз делают `uv pip install --upgrade-package yt-dlp
--upgrade-package yt-dlp-ejs "yt-dlp[default]"`: обновляются только они, `websockets` и остальное остаются как в lock. Сервер запускает yt-dlp заново на каждую
просьбу, поэтому после обновления перезапускать службу не нужно. Версию видно в итоге установки, в `check-music` и в `report.sh`. Свой `~/.config/yt-dlp/config`
сервер не читает (`--ignore-config`).

### Ограничения

- Запуск YouTube занимает около 10 секунд, и из них примерно 5 yt-dlp ждёт сам: «[download] Sleeping 5.00 seconds as required by the site». Откуда это: в ответе
  плеера YouTube для не вошедшего в аккаунт клиента есть рекламный ролик перед началом (`adPlacements`, `adSlots`), yt-dlp (`extractor/youtube/_video.py`,
  `_get_available_at_timestamp`) складывает его длительность (у ролика с пропуском берёт время до пропуска, обычно 5 с, бывает 6-10) в `available_at` каждого формата,
  а загрузчик (`downloader/common.py`) спит до этого момента, потому что до конца «рекламы» адрес звука отдаёт 403. Это делает не наш код, а yt-dlp, и обойти это
  законно нельзя: на проверке (`--simulate`/`-g`, без скачивания) клиенты tv_samsung (по умолчанию), web_embedded, mweb, tv_simply рекламу получают все, а у
  клиентов без рекламы (android_vr, ios, web_creator) нет звуковых форматов без PO-токена или нужен вход в аккаунт. Брать адрес раньше срока значило бы
  обходить рекламу, этого не делаем. Что сокращено: поток первого результата запускается ПАРАЛЛЕЛЬНО с обычным поиском (`yt-dlp ytsearch1:запрос | ffmpeg`;
  id найденного ролика yt-dlp сообщает в stderr через ~1,8 с), и если наш выбор лучшего трека совпал с ним, второй раз ролик не разбирается. Выигрыш 2-3 с;
  итог по этапам: запуск yt-dlp и поиск ~1,8 с, разбор ролика ~3,3 с, ожидание рекламы ~5 с. Если выбор другой, поток по поиску закрывается и идёт обычный путь
  (`JARVIS_MUSIC_SPECULATIVE=0` отключает). Пока идёт ожидание, Джарвис говорит «Секунду, сэр» (подсказка ИИ) и думает. Если не укладывается в
  `JARVIS_MUSIC_START_TIMEOUT`, функция отвечает `timeout` («Трек не успел начаться»). Следующие треки очереди запускаются заранее и пауз не дают. SoundCloud стартует
  быстрее (2-3 с): рекламы нет.
- SoundCloud: у треков Go+ отдаётся только 30-секундный отрывок, поэтому на таком треке музыка оборвётся на 0:30 (в логе «оборвался ... и не восстановился»).
  Если трек нужен целиком, лучше YouTube.
- Из интернета играет только то, что отдаёт yt-dlp: Spotify и Яндекс Музыка, платные подписки, закрытые по региону ролики (из-за VPN у Давида они бывают
  недоступны: `unavailable`, сервер пробует до трёх результатов поиска) не работают.
- Прокси: yt-dlp понимает http и socks, ffmpeg получает поток от yt-dlp и в сеть не ходит, а mpv на ноутбуке сам ходит за потоком и socks-прокси не умеет
  (http-прокси передаётся ему через `http_proxy`). С VPN на уровне системы (TUN) настройка не нужна.
- Колонка: плата с прошивкой старше v0.6.0 музыку не умеет, она идёт на ноутбуке. Слово «Джарвис» поверх громкой музыки слышно хуже: громкость по умолчанию 40.
- Нет таймера сна; плейлисты YouTube целиком не разбираются (очередь это результаты поиска).

### Как проверить

1. `python -m jarvis_server check-music` (как `check-pc`; его же печатает `install.sh` в итоге): что нашлось и чего нет, без сети и без звука.
2. Сказать «включи Capsize Ты любишь танцевать». В журнале (`journalctl --user -u jarvis-server -f -g "музыка"`): `музыка: «…» (youtube, track, box): найдено 5 за 1.9 с`,
   `«…» пошла за 9.6 с (поиск 1.9 с, запуск звука 7.7 с)`, потом `музыка на колонке: «…» (трек 1 из 1, громкость 40)`. В строке `TURN` этого хода `tools=play_music` и `music=box:playing`.
3. Без платы: `server/tools/fake_board.py q.wav --caps music --music-seconds 20` притворяется платой v0.6.0, принимает музыку, проверяет опережение (не больше 2 с)
   и сохраняет её в `fake_board_out/*_music.wav`.
4. Не заиграло: причина в `message` ответа функции и в журнале (`музыка: ... не дал звука: ...` с текстом yt-dlp). Частые: старый yt-dlp
   (`HTTP Error 403`, `Requested format is not available`), нет deno (`no_js_runtime`), нет сети или VPN (`network`).

| Симптом | Что делать |
|---|---|
| Джарвис говорит, что не умеет музыку, в `TURN` нет `play_music` | `JARVIS_MUSIC` не `0`; `check-music`: нет ни yt-dlp, ни mpv, ни ffmpeg; в журнале при старте `музыка: функции подключены` |
| «Колонка пока не умеет» | на плате старая прошивка: нужна v0.6.0 (в журнале при подключении `caps=-` вместо `caps=music`) |
| YouTube: `no_js_runtime` | `sudo pacman -S deno`; `./server/update_ytdlp.sh` (yt-dlp-ejs) |
| YouTube: `forbidden` / `HTTP Error 403` | `./server/update_ytdlp.sh`, потом повторить; помогает и смена узла VPN |
| YouTube: `blocked` («подтвердить, что вы не робот») | чаще всего помогает смена узла VPN или обновление yt-dlp |
| `timeout` «трек не успел начаться» | долгая реклама YouTube или медленный VPN: повторить, `JARVIS_MUSIC_START_TIMEOUT=30` или попросить SoundCloud |
| На ноутбуке играет, а `playerctl` не видит | `sudo pacman -S mpv-mpris` |
| Музыка на колонке обрывается или повторяется после разговора | журнал: `музыка: «…» оборвался на … с, перезапускаю с этого места`; смотри и `underruns` в `TURN` |

## Как добавить умение (свет и т. п.)

Функции, которые ИИ может вызывать, лежат в `server/jarvis_server/skills/`. Новое умение это обычная функция:

```python
# server/jarvis_server/skills/builtin.py
@registry.tool(description="Включить свет в комнате. Вызывай, когда просят свет.")
def lights_on(room: str, brightness: int = 80) -> dict:
    ...
    return {"ok": True, "room": room}
```

Параметры берутся из аннотаций типов (`str`, `int`, `float`, `bool`; без значения по умолчанию = обязательный),
описание из `description` или docstring. Функция может быть `async`. Исключение превращается в `{"error": ...}`, и ИИ
объяснит ошибку человеку. Реестр передаётся Gemini как набор функций, цикл вызова ручной: перед вызовом функции текст,
который ИИ уже сказал («Сейчас посмотрю»), озвучивается, пока функция выполняется. Функции: `get_time` (время и дата в часовом
поясе ноутбука; можно спросить и другой пояс), набор управления ноутбуком (раздел выше, `skills/pc/`) и музыка (раздел выше, `skills/music/`).
Набор, который должен знать про плату (музыка), кладёт свою службу в `registry.services["music"]` (её берёт `Session`), а остановку фоновых программ в `registry.add_closer(...)`.

Набор, которому нужен внешний сеанс (как Hyprland), регистрируется через `registry.register(Tool(...), available=проверка)` и
`registry.add_instructions(блок для инструкции ИИ, проверка)`: пока `проверка()` ложна, ИИ эти функции и блок не видит. Если набору нужно знать
слова человека в начале хода (подтверждения), он подписывается через `registry.on_turn(функция)`; `Session` вызывает `registry.begin_turn(текст)`.
Тексты инструкций подключаются через `persona.system_prompt(tools)`.

## Разработка и проверка

Всё из `server/`, окружение то же (`~/.local/share/jarvis/venv`) или своё по `requirements-dev.txt`.

- Тесты: `pytest` (около 990: протокол, снятие обращения «Джарвис», распознавание на подделке модели, машина состояний, деление на предложения и первого
  предложения на два куска, отсев в режиме `follow`, персона, abort и перебивание посреди ответа, числа и даты, подача звука, поиск по
  UDP, WebSocket на живых сокетах, цикл вызова функций Gemini на подделке SDK, молчание в `follow` и ворота `SilenceGate`, соединение с Google: настоящий SDK на поддельном сервере
  на localhost, скрипты установки, управление ноутбуком: поиск сеанса Hyprland, индекс приложений, argv каждой функции, подтверждение выключения; команды там идут
  в подделку `FakeRunner` из `tests/pc_fakes.py`, на настоящий рабочий стол тесты не попадают; музыка: разбор и выбор результатов поиска на подделке yt-dlp, плеер колонки на часах теста
  (темп 1 с сразу и не больше 2 с вперёд, пауза на `listen_start`, одно сообщение после каждого хода, `abort`, обрыв связи, очередь, перезапуск потока с позиции),
  ноутбук на поддельном mpv с настоящим unix-сокетом, раскодирование настоящим ffmpeg и скриптом вместо yt-dlp (`tests/music_*.py`, `test_music_*.py`)). Моделей и интернета не нужно: `tests/conftest.py` запрещает выход
  на публичные адреса, тест, который попытается достучаться до Google, упадёт сразу.
- Сквозная проверка без платы: `server/tools/fake_board.py вопрос.wav` притворяется платой (поиск по UDP или `--url`),
  отправляет WAV как 16 кГц по 40 мс, пишет хронологию сообщений, сохраняет звук ответа в WAV (звук не проигрывается),
  проверяет протокол и опережение звука. `--abort-after-audio 2` нажимает «abort» через 2 с после первого звука;
  несколько WAV подряд = несколько ходов на одном подключении (проверка памяти). `--mode wake` шлёт `listen_start` с
  `"mode":"wake"`, как плата v0.4.0, `--mode follow` с `"mode":"follow"` (по умолчанию `ptt`). Приблизительно перебивание:
  `fake_board.py a.wav b.wav --abort-after-audio 2 --pause 0`.
- Без ключа и без видеокарты: `JARVIS_LLM=mock JARVIS_TTS=mock JARVIS_STT_MODEL=mock ./server/run.sh`.
- Образец голоса для Давида: `server/tools/make_voice_zip.sh ref.wav ref.txt jarvis_voice.zip`. В образце нужен
  дословный текст, числа словами, лучше 8-12 секунд ровной речи без шума. Образец личный: в репозиторий не кладём.
- `python -m jarvis_server config` показывает итоговые настройки (без ключа), `python -m jarvis_server check-llm` проверяет Gemini.

## Если что-то не работает

| Симптом | Что делать |
|---|---|
| Установщик: «Видеокарта NVIDIA не отвечает» | поставить драйвер (команда в тексте установщика), перезагрузиться |
| В `journalctl`: `out of memory` | видеокарту занимает ещё что-то (`nvidia-smi`) или памяти мало: `JARVIS_STT_DEVICE=cpu` в `server.env` |
| Лицо платы: «Не могу связаться с ИИ. Проверь VPN» | VPN выключен, или Google недоступен из этой сети; `./server/set_key.sh` покажет, отвечает ли Gemini |
| «ИИ не принял ключ» | ключ неверный или без доступа: `./server/set_key.sh` |
| Джарвис начинает отвечать через 8-11 с (`llm_first_token_ms` в `TURN` огромный), вечером или через VPN | путь до Google медленный: в строке `TURN` смотри `llm_hedge=`. `fallback` значит, что хедж сработал и выручила запасная модель; `-` при таких задержках значит, что хедж выключен (`JARVIS_LLM_HEDGE_MS=0`) или запасных моделей нет (`JARVIS_LLM_FALLBACK` пуст). Можно снизить порог: `JARVIS_LLM_HEDGE_MS=1800`; помогает и смена VPN-узла |
| Плата не находит сервер | `systemctl --user status jarvis-server`; `sudo ufw status` (должны быть UDP 47800 и TCP 47801 от 192.168.0.0/16); адрес вручную в консоли платы |
| Речь после пробуждения ноутбука не работает | сбой видеокарты после сна: сервер сам перезапускается (`Restart=on-failure`), занимает около минуты |
| Плата слушает после слова «Джарвис», но не отвечает | в логе `TURN empty(wake_only)`: распознано только имя (сказано «Джарвис» и пауза); `empty(no_speech)` или `empty(silence)`: плата услышала тишину; `empty(junk)`: Whisper выдумал фразу из шума, отброшена |
| Джарвис молчит на фразу без слова «Джарвис» (режим `follow`) | в логе `follow: отброшено (filler|low_conf): ...` и `TURN empty(filler)` / `empty(low_conf)`: это междометие или Whisper не уверен в распознавании. Слишком много отсева: `JARVIS_FOLLOW_MIN_LOGPROB=-1.3` (мягче) или `JARVIS_FOLLOW_GUARD=0` (отвечать на всё) |
| Джарвис отвечает на болтовню или видео в комнате (режим `follow`) | в логе `Вы (follow): ...` без `follow: промолчал`: ИИ не вывел пометку, а в `TURN` нет `silent(...)`. Фраза с именем «Джарвис» в любом месте отвечается всегда (так задумано). Проверить подводку: `server/tools/follow_silence_eval.py --yes`; убедиться, что `JARVIS_FOLLOW_SILENCE` не `0` |
| Джарвис молчит, когда к нему обращались (`follow`) | в логе `follow: промолчал (not_addressed): «...»; причина: ...` и `TURN silent(...) why=...`: ИИ решил, что фраза не к нему. Подправить подводку в `addressing.py` или `JARVIS_FOLLOW_SILENCE=0`. Человек может повторить со словом «Джарвис» |
| Первая фраза после паузы всё равно медленная, в `TURN` `llm_conn=new` | рукопожатие с Google на пути хода: смотри строку лога `ИИ: соединение открыто за ... мс (прогрев ...)` и долю `new` в `report.sh`; `JARVIS_LLM_KEEPALIVE_S` больше или меньше, `JARVIS_LLM_PREWARM=0`, если прогрев не помогает |
| Не уверен, что происходит | `./server/report.sh` и прислать файл Мирославу |

## Лицензии и приватность

OmniVoice: код Apache-2.0, веса CC-BY-NC (в личных целях можно, коммерчески нельзя). Whisper (MIT), faster-whisper (MIT).
К Google уходит только распознанный текст разговора, его краткая история (последние 20 обменов) и ответы функций управления
ноутбуком (названия программ и треков, заголовки окон не уходят); звук микрофона и голос остаются на ноутбуке. В режиме `follow` туда же
уходит текст всего, что услышала плата без слова (в том числе чужая болтовня: по нему ИИ решает, молчать ли), но молчаливый ход в историю
следующих запросов не попадает. Прогрев соединения (`HEAD` на корень хоста) не несёт ни ключа, ни текста. В лог попадают распознанные фразы
и ответы, поэтому перед отправкой `report.sh` стоит бегло глянуть
в файл. Ключ хранится в `~/.config/jarvis/server.env` с правами 600 и нигде не печатается.
